## Publication provenance

The release workflows intentionally validate pull requests through GitHub's merge-test ref. A PR-triggered Release Candidate artifact can therefore contain the correct deterministic extension ZIP while its release manifest records the temporary merge-test SHA.

The fully passing release-handoff RC run `31267525400` was inspected directly:

- `webcap-0.2.0.zip`: **1,341,084 bytes**;
- SHA-256: `8bade485ee0672a2b160abf59f45c1772062ffc00724889c5aaa39294e7edb34`;
- 25 extension package entries;
- packaged `manifest.json` version: `0.2.0`;
- `webcap-0.2.0.release.json.sourceCommit`: `fc91c80c524895f8a46f2b40ceb0e27e745f5e93`, the PR merge-test ref for that run.

This is valid PR validation evidence, not final publication provenance. The **canonical 0.2.0 publication artifact must be generated by the Release Candidate workflow triggered by the final `v0.2.0` tag**. Before GitHub Release or Chrome Web Store publication, the release owner must verify that the tag-triggered artifact keeps the expected ZIP size/SHA and that its release manifest `sourceCommit` exactly matches the commit referenced by `v0.2.0`.

## Boundaries

No backend, telemetry, analytics, remote executable code, new required permission or default host permission. No GitHub Release, Chrome Web Store upload, review submission or publication is performed until the final tag-triggered provenance gate passes.
